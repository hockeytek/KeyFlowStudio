Cloud GPU Setup for KeyFlow Studio

This guide covers the full setup path from an empty AWS account to a working cloud GPU inside the application. It is based on what the app actually does through AWS APIs and SSH. If you skip some of these steps, parts of the Cloud (AWS) UI will be incomplete or will not show correct data.

In short: the app needs more than just an EC2 instance. It needs an AWS profile with the right permissions, a region, an EC2 key pair, a security group, GPU quota, a public or custom AMI, SSH access and, if you want the billing panel, Cost Explorer enabled.

What the application uses in AWS

Service / API Purpose Required
EC2 List instances, start, stop, delete, create new GPU instances, search AMIs, list key pairs and security groups. Yes
STS Validate AWS credentials through GetCallerIdentity. Yes
Pricing API Show current On-Demand pricing for the selected instance type. Recommended
EC2 Spot Price History Show current Spot pricing and availability zone. Recommended
Cost Explorer Show month-to-date cost, yesterday's cost and end-of-month forecast. Required if you want the billing panel
Service Quotas Read G/VT Spot and On-Demand quota so the UI can filter to realistically launchable GPU types. Recommended

You do not need to deploy extra AWS infrastructure besides EC2. But your account and IAM permissions must allow the app to read pricing, quotas and billing if you want the Cloud UI to be complete.

What you need to create or enable first

  1. An AWS account with billing enabled.
  2. An IAM user or profile with programmatic access.
  3. An Access Key ID and Secret Access Key.
  4. AWS CLI on your local machine, or credentials entered directly in the app dialog.
  5. An EC2 key pair in the same region where you will launch the instance.
  6. A security group with SSH and worker API access on port 8080.
  7. Sufficient GPU quota in the selected region for Spot and/or On-Demand.
  8. Cost Explorer enabled if you want cost information inside the app.

Minimal IAM permissions

The policy below matches the real application code. It is not the only option, but it is a practical minimal read/write set for correct operation.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "sts:GetCallerIdentity",
        "ec2:DescribeInstances",
        "ec2:StartInstances",
        "ec2:StopInstances",
        "ec2:TerminateInstances",
        "ec2:RunInstances",
        "ec2:ModifyInstanceAttribute",
        "ec2:DescribeImages",
        "ec2:CreateImage",
        "ec2:CreateTags",
        "ec2:DescribeKeyPairs",
        "ec2:DescribeSecurityGroups",
        "ec2:DescribeSpotPriceHistory",
        "ec2:DescribeInstanceTypeOfferings",
        "ec2:DescribeInstanceTypes",
        "pricing:GetProducts",
        "ce:GetCostAndUsage",
        "ce:GetCostForecast",
        "servicequotas:GetServiceQuota"
      ],
      "Resource": "*"
    }
  ]
}

If you do not need the billing panel, you can remove ce:*. If you do not need live instance pricing in the UI, you can remove Pricing and Spot history access, but that part of the UI will stop being useful.

Security group rules

Rule Purpose Recommendation
Inbound TCP 22 SSH for worker bootstrap, environment checks and watchdog installation. Restrict to your IP or VPN.
Inbound TCP 8080 HTTP API for the cloud worker. Restrict to a trusted IP range. Do not leave it open to the internet unless you understand the risk.
Outbound all Needed for apt, pip, Hugging Face, GitHub Releases and API calls. The default allow-all egress usually works.
Important: the worker listens on plain HTTP on port 8080 and does not use its own authentication layer. Security depends on your security group and source IP restrictions.

Which instance type to choose

The application keeps its own GPU catalog and prefers modern single-GPU options with 24 GB VRAM. That is why the UI usually prioritizes g5 and g6 families.

Type GPU VRAM vCPU Notes
g5.xlarge NVIDIA A10G 24 GB 4 Baseline recommended option. Quick create uses this by default.
g5.2xlarge NVIDIA A10G 24 GB 8 Good if you want a bit more CPU headroom for worker and ffmpeg.
g5.4xlarge NVIDIA A10G 24 GB 16 Better for heavier graphs and more comfortable background processing.
g6.xlarge / g6.2xlarge / g6.4xlarge NVIDIA L4 24 GB 4 / 8 / 16 Modern alternative when G6 is offered in the region.
g4dn.xlarge / 2xlarge / 4xlarge NVIDIA T4 16 GB 4 / 8 / 16 Older budget family. VRAM can be tight for some workloads.
p3.2xlarge / p3.8xlarge NVIDIA V100 16 GB 8 / 32 Older and often expensive. Use only if your region does not offer better options.

For a pragmatic starting point, choose Spot + g5.xlarge to minimize cost or On-Demand + g5.xlarge / g5.2xlarge for stability.

How AMI works in the app

1. Preferred option: your own KeyFlow Studio AMI

After the first successful bootstrap, create your own AMI from the instance. The app tags it with App=KeyFlowStudio and SourceInstanceId=..., then searches for these AMIs first on later launches. This is the best long-term workflow.

2. Automatic public GPU AMI detection

If no custom AMI exists yet, quick create tries to find a public Ubuntu 22.04 GPU Deep Learning AMI. The app searches by AMI name pattern instead of a hardcoded AMI ID because IDs are region-specific and change over time.

The code looks for names matching patterns like:

  • Deep Learning Base OSS Nvidia Driver GPU AMI ... Ubuntu 22.04
  • Deep Learning OSS Nvidia Driver AMI GPU PyTorch ... Ubuntu 22.04
  • other public AMIs that contain GPU + Ubuntu 22.04 + Deep Learning

3. Manual AMI selection

The Browse AMIs... button lists all AMIs owned by your account in the current region. Use this when you already have one or more private images and want to choose the exact one.

What the UI shows for pricing

  • Current instance price shows live Spot or On-Demand pricing for the selected type.
  • Month / yesterday / forecast come from Cost Explorer.
  • The launch-type picker tries to show hourly pricing next to each instance type.
Important: exact numbers always depend on region, availability zone, current Spot market and your account. The app does not use hardcoded prices. Use the live AWS-backed values in the UI, not old screenshots or notes.

Extra costs to keep in mind:

  • EBS root volume: the app launches with gp3 60 GB.
  • Public IPv4 address.
  • Outbound data transfer.
  • AMI and snapshot storage after you create your own images.

Full first-time setup flow

  1. Create an IAM user or profile for the app.
    Prepare an Access Key ID and Secret Access Key.
  2. Enable Cost Explorer if you need the billing panel.
    Without it, the cost widgets will stay empty or show errors.
  3. Check GPU quotas in your target region.
    Spot and On-Demand quotas are separate. If the instance type you need does not appear, the issue is usually quota or regional availability.
  4. Create an EC2 key pair.
    Download the .pem file and store it locally, for example ~/.ssh/keyflow-gpu.pem.
  5. Create a security group.
    Open inbound TCP 22 and TCP 8080 only to your IP or a trusted range.
  6. Configure your AWS profile locally.
    If you prefer CLI, run:
aws configure --profile keyflow

Or enter credentials directly in the app using the Set up credentials... button.

  1. Open Settings → Cloud (AWS).
    Fill in AWS Profile, Region, SSH key path and SSH user.
  2. Open Instance Manager.
    This is where AMI, key pair, security group, Spot/On-Demand mode and the current instance list are managed.
  3. If you do not have a custom AMI yet, use 1-click: Create GPU.
    The app tries to:
  • find a public Ubuntu 22.04 GPU AMI,
  • pick g5.xlarge,
  • launch it as Spot,
  • create a gp3 60 GB root volume,
  • attach the selected key pair and security group.
  1. Wait for the instance to reach Running state and select it.
    Double-clicking the instance in the list fills the Instance ID and IP automatically.
  2. Click Check Environment.
    The app first runs an SSH inspection. If the worker, venv, dependencies or models are not ready, it offers to install everything automatically. Accept that prompt.
  3. Wait for worker bootstrap to complete.
    At this stage the app:
  • copies the cloud worker bundle via SSH,
  • creates or updates ~/keyflow-venv,
  • installs Python dependencies,
  • downloads MatAnyone2, BiRefNet and GVM models,
  • starts the worker on port 8080,
  • checks /health.
  1. After the first successful run, create your own AMI.
    In the instance manager: right-click the instance → Create AMI. This makes later launches much faster because the worker and models are already baked into your image.
  2. Optionally install the watchdog.
    It shuts the instance down automatically after a long GPU idle period so you do not accidentally leave an expensive instance running.
  3. Enable Cloud GPU and use the application normally.

Normal day-to-day workflow after setup

  1. Open Cloud (AWS) settings.
  2. Start the instance or select it from Instance Manager.
  3. Wait for Running state and a valid public IP.
  4. Use Check Environment if the local cloud bundle changed and you need to resync the worker.
  5. Run cloud jobs from the main window.
  6. Stop the instance when finished, or rely on the watchdog if you installed it.

How the app fields map to AWS

Field in the app Meaning
AWS profile The profile name from ~/.aws/credentials or from the built-in credentials dialog.
Region The EC2 region that contains the instance, key pair, security group and AMI.
Instance ID The EC2 instance identifier, for example i-0123456789abcdef0.
SSH key The local path to your .pem private key file.
SSH user Usually ubuntu for Ubuntu/DLAMI. On Amazon Linux it is often ec2-user.
AMI The image that new instances will use in the instance manager.
EC2 key pair The AWS key pair name attached to a newly launched instance.
Security group The SG that allows SSH and the worker API.
IP / hostname The public worker address. Usually filled automatically, but you can override it manually.

Limitations and important caveats

  • Spot can be interrupted. If AWS reclaims a Spot instance, the current job is interrupted. Use On-Demand for stability.
  • The worker only processes one job at a time. This is intentional because of GPU memory limits.
  • Port 8080 must be reachable. SSH alone is not enough for cloud processing to work.
  • Terminate deletes the root EBS volume. The app launches instances with DeleteOnTermination=True, so do not keep unique data only on the instance disk. Use AMIs, snapshots or download results.
  • Old private AMIs are not removed automatically. Clean up unused AMIs and snapshots periodically.
  • Quick create is designed around Ubuntu 22.04 GPU AMIs. That is why the default SSH user should normally stay ubuntu.

Troubleshooting

Billing widgets do not show anything

  • Make sure Cost Explorer is enabled.
  • Check ce:GetCostAndUsage and ce:GetCostForecast permissions.

The GPU instance list is empty or incomplete

  • Check G/VT Spot and On-Demand quotas.
  • Check whether the region actually offers G5 or G6.

The app cannot find an AMI automatically

  • Try another region.
  • Select an AMI manually from the list.
  • After the first successful bootstrap, create and keep using your own AMI.

SSH works but cloud processing does not start

  • Check the inbound TCP 8080 rule.
  • Run Check Environment and wait for a successful health check.

SSH access fails

  • Make sure you selected the correct .pem file.
  • Check the security group rule for port 22.
  • Use ubuntu for Ubuntu and ec2-user for Amazon Linux.
